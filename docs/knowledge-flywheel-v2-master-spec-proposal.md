# 目鏡大叔 Knowledge Flywheel｜知識複利飛輪 2.0（Master Spec 提案）

> **狀態：設計提案／未驗收／不改動現有引擎。**
>
> 文件性質：增量式架構與治理契約草案；以現有 `BRAIN-ARCHITECTURE.md`、`SYSTEM-MEMORY-SCHEMA.md`、`KNOWLEDGE-COMPILER-PROTOCOL.md`、`.agents/workflows/knowledge-compiler.md`、`obsidian-vault/` 和 KDF 審核程序為前提。**不另建第二套 Knowledge Store，不以新文件覆蓋既有 KDF Schema、MCP Bridge、同步程式。**

## 0｜不可更改的北極星

**知識不是因為被收藏而複利，而是因為被使用、質疑、驗證、修正、重新組合，令下一次判斷更可靠、下一次創作更有深度。**

目標不等於文章數、卡片數、粉絲數；目標是「把真實問題轉成有來源且可回寫的判斷資產」，同時產生：
1. **知識複利**：新研究讓舊卡片更精準，跨卡形成新理解；
2. **內容複利**：一組可信論證能適配文章、影片、教學、FAQ、工具；
3. **信任複利**：確實說明證據與不確定性，保留公開更正能力；
4. **問題／受眾複利**：真正的提問與反對意見讓下一輪研究更貼近人。

內容觸及與商業成效可做為後端觀察指標，**不能當作醫學主張為真的證據**。

## 1｜四個模組的責任界線

| 模組 | 負責的問題 | 核心產物 | 不做的事 |
| --- | --- | --- | --- |
| Zettelkasten 卡片盒 | 這項研究讓我形成什麼可獨立論證的看法？它連到哪個舊觀點？ | Literature Note、Atomic Note、Structure Note、有語義的連結 | 只複製摘要、不檢驗論點 |
| Second Brain 第二大腦 | 要放哪裡、怎麼找、何時該浮現？ | Obsidian Vault、Inbox、MOC、版本、任務、檢索 | 把所有碎片自動升級正式知識 |
| KDF 知識治理引擎 | 來源可信嗎？可以說到哪裡？何時能變成決策規則？ | Provenance、Evidence／Observation 分離、Human Gate、Ledger、成熟度與審核 | 讓 AI 推論自動變成臨床事實 |
| Knowledge Flywheel 複利迴圈 | 哪裡真正用到了？收到了什麼問題？哪張卡應被更新？ | 知識→應用→回饋→再研究的追溯閉環 | 把留言、點讚當療效研究 |

**KDF 是既有領域治理核心，不是這份 SOP 新發明的第二個資料庫。**

## 2｜中央循環（先保持最小）

`現場／讀者問題 → 收集並定義問題 → 研究與查證 → 文獻卡 → 原子論點與跨卡連結 → 人工審核的知識節點 → 衛教／教學／文章／產品應用 → 現場與讀者回饋 → 新問題／修正舊卡`

### 關卡 A：捕捉問題（Problem Capture）
- 記錄問題原句（若不確定是否逐字則標「意譯」）、時間、來源類型、使用情境、誰會因此做決定。
- 個案、客人、學生不留可辨識個資於公開 Repo；需要個案資料須放授權私有系統。
- 一個問題可連多篇研究；一篇研究可服務多個問題。

### 關卡 B：證據與缺口（Research / Evidence）
- 優先搜尋現有已編譯卡，再搜尋新文獻；以 DOI／PMID／canonical URL 去重。
- 來源分為：研究直接結果／系統性回顧／臨床指引或共識／現場觀察／工作假說／AI 推論，不得混欄。
- 效果量、分母、單位、追蹤期、信賴區間與適用族群需保留；只讀摘要時必須標「未核對全文」。
- 「沒有顯著差異」不等於「已證明沒有影響」；「相對風險下降」不等於「絕對風險下降」。

### 關卡 C：文獻筆記（Literature Note）
- 一份可引用的研究來源對應一張 canonical 文獻卡；保留原始結果、重要限制及引用連結。
- 文獻卡不等於作者自己的永久觀點；不能只是把 AI 摘要存進 `04-知識卡片/`。
- 先檢查既有卡片，有同 DOI 的記錄先補強原卡，不另造重複。

### 關卡 D：原子論點（Atomic Zettel）
- **一張卡，一個可質疑的完整句命題**；將研究結果、個人詮釋、臨床衛教的界線分清楚。
- 應連回至少一項可追溯的來源，以及一項有語義的相鄰／對照概念。
- 建連結時要說明關係：`supports`、`challenges`、`qualifies`、`applies_to`、`raises_question`。不是「凡是同標籤就全部互連」。
- 新研究優先修正既有論點；**新命題**才新建卡片。保留原版與修訂理由。

### 關卡 E：知識成熟（KDF Human Gate）
沿用既有生命週期：
`RAW CAPTURE → CLAIM → CANDIDATE KNOWLEDGE → VALIDATED KNOWLEDGE → DECISION RULE → CORE OS`。
- 升級須通過來源／方法／數據／適用範圍／矛盾檢查與人審。
- 任一節點可因新證據降級、撤回或封存；不得在無審核紀錄下由 AI 靜默升級。
- 「實作完成」不等於「驗收完成」，Bridge 或同步功能仍須各自驗證。

### 關卡 F：應用（Apply / Publish）
- 每個重要對外主張都連向來源文獻與原子卡；文章是**知識的一次輸出，不是知識的終點**。
- 輸出形式：門市 Q&A／衛教講座／教學投影片／Facebook／Blog／影片／網站問題頁／工具。
- 寫作可以溫暖、有故事，**引文、統計結論、臨床適用性不能因此被改寫誇大**。
- 原稿、審核稿、已發布 URL 與修正紀錄分開；不自動對外發布。

### 關卡 G：回饋與再編譯（Feedback → New Question）
- 留言、提問、店內對話、課堂困惑、網站搜尋需求、勘誤各自成為**訊號卡（Signal）**。
- 訊號 ≠ 研究證據；需判別是「新研究問題」「表達不清」「個別需求」「可能的錯誤」或「不需處理」。
- 回寫：修訂既有原子卡、增加限制、提出反例、補研究缺口、改教學表達；每次都記變更理由與來源。
- 公開內容如已傳播錯誤資訊，應安排勘誤與版本回鏈；不可只修知識庫不處理外部誤解。

## 3｜三層儲存不是三份互相競爭的母本

**現行規則（核對於 2026-11-13）**：`tornadolee20/optometry-notes/obsidian-vault/` 被既有規範指定為唯一長期 Obsidian 母本；GitHub 是版本管理與跨代理協作。此 Repo 為 **public**。

- Raw／staging：`obsidian-vault/00-收件匣/`；待審，不自動對外使用。
- Evidence：`obsidian-vault/02-文獻與期刊/`；與既有 KDF Evidence Card 約束相容。
- Atomic / Knowledge：`obsidian-vault/04-知識卡片/`；沿用既有正式 KDF 路徑 `04-知識卡片/KDF/`，不搬遷舊卡。
- Structure：`obsidian-vault/01-專家與MOC/`。
- Workflows：`obsidian-vault/05-營運SOP與模板/`；Templates：`06-模板 (Templates)/`。
- Application：`07-長篇專欄與企劃/`、`10-歷史文章智庫/`；正式 KDF 仍遵循現有 `07-長篇專欄與企劃/KDF/`。
- Google Drive《醫事寫作力》用於課程產品與應用連結，不複製研究母稿。
- Growth OS 接正式發表後的 SEO/GEO、內容成效，提供訊號，不接管研究真偽。

**當前跨倉庫衝突（必須解決）**：另有私人 `tornadolee1720/obsidian-private-20261109-145449` 包含 2026-11-13 咖啡／茶研究候選卡與新 SOP。兩個 Repo 不可都自稱 canonical。**此提案不複製私人內容進公開 Repo，不變更主母本設定，也不假設桌機已同步。**後續須比對差異，確認哪個 Vault 真正開啟，再做經審核的安全遷移／指向關係；尤其個案與未公開研究不可誤推到 public。

## 4｜最小資料契約：現有 Schema 延伸，而非取代

所有卡維持 Markdown + YAML，保留既有欄位；新增欄位先作 **proposal**、經既有 KDF Schema 與 validator 相容性檢查後再採用。

| 欄位 | 意義 |
| --- | --- |
| `id` / `type` | 穩定身份、card 類型，不依檔名推論 |
| `status` / `review_required` | 待審、有效、遭挑戰、封存；人審狀態 |
| `source_ids` / `source_urls` | DOI / PMID / URL，可追溯 |
| `claim` | 一張原子卡的一句主要主張 |
| `basis` / `interpretation` | 研究事實與自己的解釋必須分離 |
| `population` / `outcome` / `time_horizon` | 適用族群、結局、時間尺度 |
| `limits` / `contradictions` | 例外、不確定與相反證據 |
| `relations` | 指向其他節點且具關係型別 |
| `reviewed_by` / `reviewed_at` / `revision_reason` | 誰審核、何時修、為何修 |
| `application_links` / `feedback_links` | 用在哪裡、回饋來自哪裡 |

**不得預設人審已完成；也不得虛構來源 URL、訪談逐字、療效或量測值。**對外可用的 Node 必須能經由 source IDs 回到原始文獻。

## 5｜多代理分工（沿用現有架構）

- **Jarvis**：低摩擦擷取現場問題、網址、語音重點；不批准臨床證據。
- **Antigravity／前處理工具**：去重、提取來源、格式化、比對候選卡；不批准正式 Schema／臨床結論。
- **ChatGPT／Claude／Codex**：研究比對、跨卡推理、提出矛盾、整理草稿、提出可驗證的修訂建議。
- **目鏡大叔本人**：專業判斷、升級／降級、臨床衛教立場、發布與更正批准。
- **Obsidian**：正式知識與圖譜的閱讀、寫入入口；**GitHub**：版本與稽核；**KDF**：流程與證據治理，非另一份內容庫。

## 6｜複利衡量：量「知識被改變」，不是只量「收了多少」

每週最小指標（先不建資料庫，使用 Markdown 審核表記錄）：
- **可追溯率**：可回到原文來源的已發表實質主張／全部已發表實質主張。
- **重用率**：本週真正被兩個以上不同應用引用的已審論點數（去重）。
- **修訂率與原因**：有新證據進來後，舊卡被補強、限縮、挑戰的數量及理由。
- **衝突待辦**：尚未解決的來源矛盾、數據出入與審稿阻塞。
- **回饋轉化率**：有明確新研究問題或需要修稿的訊號／已分流有效訊號。
- **審核積壓**：卡在待審超過 14 天的高價值材料；優先降低而非追求大量建卡。

以上是管理設計指標，不是目前已量得的績效數字，也不聲稱一定會提升觸及或銷售。

## 7｜兩段式驗證，不跳過既有 Gate

### Phase 1：14 天、3 個真實問題的無破壞試行
- 選三題不同難度：例如飲品與眼睛、兒童近視、熟齡視覺（不需都發表）。
- 每題完整走：原問題 → 來源查證 → 現有卡去重 → 一至三張原子卡候選 → 索引 → 應用 → 至少一次回饋分類或後續待追問。
- 先記錄基線與每題作業耗時，觀察「每篇研究是否真的改變舊知識」，不是比筆記數目。
- 原則：只寫隔離分支／待審資料；不可改既有 KDF 正式卡狀態或發布工具。

### Phase 2：完成契約驗收才接自動化
- 對齊已有 KDF Node Schema、Ledger、Human Gate、MCP Bridge 與同步配置。
- 再做去重與來源查核輔助、連結檢查、孤兒卡與矛盾待辦；不先打造大型 Dashboard、資料庫或全自動知識圖譜。
- Google Drive / Social / Web 的輸出皆須以穩定 Node ID 連回母本，且仍需人工審查醫療內容。

## 8｜需要簽核的架構決策（不得在工具呼叫中偷渡）

1. **唯一母本的實際位置**：現有 public `tornadolee20/optometry-notes` vs 現在存在的 private Vault；先比對差異、權限與 Windows 開啟目錄，再決定是否安全整併。
2. **正式 KDF 卡片格式**：本提案新欄位是否能被現有 Bridge／validator 接受，未確認前模板僅能用於候選卡。
3. **卡片升級／發布權限**：人工 Gate 的簽核紀錄與高風險內容限制。
4. **已發布文章回鏈**：避免引用草稿或替換已發表原文而沒有更正紀錄。

## 9｜成果定義

一題完成不是「寫出很漂亮的文章」，而是能完整回答：
- **問題從哪裡來？**（經去識別化的脈絡）
- **我們知道什麼？**（研究事實與來源）
- **還不知道什麼？**（缺口、反例、衝突）
- **目鏡大叔現在主張什麼？**（自己的原子論點和適用範圍）
- **被用在哪裡？**（文章／教材／門市）
- **因為回饋改變了什麼？**（舊卡修訂、下一個研究問題）

> **原則：AI 可以提議知識，不能代替你決定什麼該成為『目鏡大叔的判斷』。**
