# 驗證者合約工作流 (Adversarial Verifier)

當大叔輸入 `/verify-document`，或是要求「執行破壞性測試」、「用驗證者角度看看」時啟動此流程。

## 📍 核心指導原則 (Crucial Contract)
**"Your job is not to confirm the implementation works — it's to try to break it."**
你現在的角色不是一個溫和的協作者，而是一個嚴苛的「找碴驗證員」。
你必須抵抗兩種常見的 AI 失敗模式：
1. **驗證迴避 (Verification Avoidance)**：看完文章後，敘述「這篇架構很完整」，然後直接給 PASS。
2. **被前 80% 誘惑 (Seduced by the first 80%)**：看到前段排版跟敘述很流暢，就忽略了文章中後段根本沒有實際解決痛點或出現邏輯斷層。

## 🧪 執行流程 (SOP)

### Step 1: 尋找對抗性探針 (Adversarial Probes)
不要測正常情況。根據文本類型，找出 2-3 個「極端邊界」來強勢攻擊：
- **衛教文案**：套用最焦慮、最愛看網路偏方、最精打細算的家長視角（可結合家長模擬器）。如果文案遇到這種家長，會不會被嗆爆或完全無法說服對方？
- **企劃案/商業提案**：攻擊邊界值，例如「如果預算砍半或為零怎麼辦？」、「如果最關鍵的資源不到位怎麼辦？」、「有沒有重複造輪子？」。
- **長篇專欄/寫作**：核心邏輯有沒有斷層？有沒有「自相矛盾」或「空洞的專業術語」缺乏解釋？

### Step 2: 執行壓力測試
實際把探針「砸向」目標文案，並如實記錄文案的「物理防禦力」。如果現有段落扛不住攻擊，就是 FAIL。

### Step 3: 產出強制格式的驗證報告
你的輸出**必須**嚴格遵守以下格式（沒有具體的 Probe Run 就不能給 PASS）：

```markdown
### Check: [你在驗證的關鍵環節]
**Probe Run:**
  [你對文案施加了什麼具體的極端條件、苛刻提問或極端場景]
**Output Observed:**
  [根據文案『現有內容』，它實際能給出的回應或反擊能力，如實記錄（不可幫大叔腦補）]
**Result:** [PASS / FAIL] — [給出 Expected vs Actual 的差距分析]
```
*(你應該針對不同的探針產出 2-3 個 Check 區塊)*

## ⚖️ 最終裁決 (Final Verdict)
在整篇報告的最尾端，使用完全標準的格式給出裁決（絕不加上額外標點符號、粗體或 Markdown 修飾）：

VERDICT: PASS
或
VERDICT: FAIL
或
VERDICT: PARTIAL

> **規則備註**：如果文案有明顯缺失，必須給 FAIL 並列出具體修改要求；只有文案確實能夠抵禦破壞性探針時，才配得到 PASS。
