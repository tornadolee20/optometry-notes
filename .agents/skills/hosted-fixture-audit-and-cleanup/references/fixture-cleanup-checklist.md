# Fixture Cleanup Checklist

在宣稱 cleanup 完成前，逐項確認：

- [ ] 已有 Fixture ID 清單，且清單是在建立當下即時記錄的（不是事後回想重建）
- [ ] 清單中每一筆都帶有本次 execution window 的唯一標記
- [ ] 刪除順序已考慮參照/外鍵關係（子 → 父）
- [ ] 刪除操作只針對清單中的 ID，未使用會誤中其他資料的寬鬆條件
- [ ] 每批刪除後記錄實際刪除筆數，並與清單筆數核對一致
- [ ] 用唯一標記重新查詢，residual count 為 0
- [ ] 若 residual count 非 0，已記錄原因並標記為 `PARTIAL`（不得標記 `PASS`）
- [ ] 已將清除後的資源狀態與 baseline 比對
- [ ] 若目標包含 production，已附上明確授權記錄
- [ ] 最終報告使用 SKILL.md 的最終報告模板，狀態詞彙符合共用規範

## 常見失敗模式（需特別檢查）

- **模糊條件清除**：用「前綴相似」而非「清單中的確切 ID」刪除，可能誤刪或漏刪。
- **忽略衍生資料**：驗證行為觸發了額外的寫入（如自動產生的關聯紀錄），但未列入
  Fixture ID 清單，導致清除不完整卻沒被發現。
- **residual count 查詢條件與建立時不一致**：例如建立時用大小寫敏感的標記，
  查詢時卻用大小寫不敏感比對，造成誤判為 0。
- **把「清除指令執行成功」等同於「資料已清除」**：必須用獨立的 residual count
  查詢驗證，而不是只看刪除指令本身沒有報錯。
