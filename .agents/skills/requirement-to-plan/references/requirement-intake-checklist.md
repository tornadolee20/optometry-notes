# Requirement Intake Checklist

在開始拆解計畫前，先逐項確認以下資訊是否齊備。缺項不代表停止，但必須明確
標記為 `OPEN QUESTION`，不得自行補造。

- [ ] **Original request**：需求的原始文字或口語敘述，盡量保留原話，不要
      在此階段就改寫成解法。
- [ ] **User goal**：使用者實際想達成的結果，而不是他們提出的解法。
- [ ] **Business goal**：這個需求對產品或商業指標的預期影響。
- [ ] **Current pain**：目前的痛點或缺口是什麼，如何被發現（觀察、回饋、
      資料訊號）。
- [ ] **Stakeholder**：誰是這個需求的 owner，誰需要被諮詢，誰只需要被
      告知。
- [ ] **Urgency**：時程壓力來源與硬性截止日期（若有）。
- [ ] **Constraints**：技術、法律、預算、人力或既有架構上的限制。
- [ ] **Protected behavior**：現有哪些功能或資料流程不能被這個需求破壞。
- [ ] **Known facts**：目前已經確認、可直接引用的事實（附來源）。
- [ ] **Assumptions**：目前依賴但尚未驗證的假設。
- [ ] **Open questions**：需要 owner 或其他證據才能回答的問題。

## 常見疏漏

- 把使用者提出的「解法」直接當成「需求」記錄，導致 scope 從一開始就被
  提案的技術路徑綁死。
- 把尚未確認的假設寫成既定事實，後續 slice 全部建立在錯誤基礎上。
- 遺漏 stakeholder，導致計畫完成後才發現真正的 owner 另有其人。
- 用「應該沒問題」帶過 constraints，未來實作階段才發現架構不支援。
