# Negative Proof Patterns

四種「安全停用修復」方式的取捨，依專案實際工具鏈選用其一：

## 1. Skip flag（測試層面）

適合：修復程式碼難以乾淨隔離，但測試本身可以暫時標記。

```text
1. 在目標測試加上明確標記（例如標記為 xfail/skip，並附註解說明這是為了
   negative proof 暫時加上，不是永久跳過）
2. 移除標記後才算「已恢復」——不得留下任何跳過標記在最終提交中
```

風險：只驗證了「測試本身」而非「修復程式碼」，需搭配確認修復程式碼路徑
確實被該測試觸發到。

## 2. Feature flag

適合：修復本來就包在功能開關後面。

```text
1. 暫時把開關切到「舊行為」
2. 跑測試，確認失敗
3. 切回「新行為（含修復）」
4. 跑測試，確認通過
```

風險：若開關粒度太粗，可能連帶關掉其他無關功能，需確認影響範圍。

## 3. Temporary patch

適合：沒有 flag 機制，修復是直接的程式碼變更。

```text
1. 建立一個明確標註「TEMPORARY - negative proof only, revert before commit」
   的暫時性還原改動（把修復的程式碼邏輯還原成修復前的樣子）
2. 跑測試，確認失敗
3. 撤銷這個暫時性改動（確認 diff 完全乾淨）
4. 跑測試，確認通過
```

風險：手動還原容易漏改，建議還原後用 diff 逐行核對，而不是憑印象修改。

## 4. Isolated commit + revert

適合：修復已經是獨立 commit。

```text
1. git revert <fix-commit-sha> --no-commit
2. 跑測試，確認失敗
3. git checkout . (或等效指令，恢復到 revert 之前)
4. 跑測試，確認通過
```

風險：若修復 commit 與其他改動糾纏在一起，revert 可能連帶動到不相關內容，
需要先確認該 commit 範圍夠乾淨。

## 共同陷阱

- 忘記在負向證明後恢復修復，導致最終提交仍是「壞的」版本。
- 只跑了受影響的單一測試檔，沒有確認同一輪還有沒有其他測試也應該一起失敗
  又一起通過（同根因的相鄰測試）。
