# False-Positive Test Checklist

在宣稱「regression 已修復」前，逐項確認：

- [ ] 已明確寫下 bug 的可觀察症狀（輸入/預期輸出/實際輸出）
- [ ] 已記錄修復前基準（測試套件整體通過/失敗概況）
- [ ] 已選定一種「安全停用修復」的方式，並記錄選用原因
- [ ] 停用修復後，實際執行測試並讀取 **exit code**（不是只看終端文字顏色）
- [ ] exit code 確認為非 0（失敗），且失敗的是預期的那個 assertion
- [ ] 沒有使用 `|| true` 或等效寫法遮蔽失敗訊號
- [ ] 若停用修復後測試意外通過：已停下來先修測試本身，未直接宣稱 bug 已修
- [ ] 已完整恢復修復（撤銷所有暫時性改動）
- [ ] 恢復後重新執行測試，exit code 為 0，且是同一個 assertion 通過（不是
      被替換成更寬鬆的斷言）
- [ ] `git status` / 工作區已確認乾淨，無殘留的暫時性改動
- [ ] 最終報告同時包含負向證明與正向證明兩部分

## 常見假陽性成因

- **斷言太寬鬆**：測試只檢查「沒有拋出例外」，而不檢查具體回傳值，導致修復
  前後都能通過。
- **測試沒有真的觸發到修復路徑**：例如 mock 掉了關鍵依賴，導致修復程式碼
  根本沒被執行到。
- **停用修復不完整**：只改了程式碼的一部分，另一處仍保留修復邏輯，導致
  「停用後」測試仍意外通過。
- **把 build/lint 的成功當成測試通過**：型別檢查或建置成功不等於行為驗證
  通過，需明確區分（見 `../_shared/references/engineering-principles.md` A 節）。
