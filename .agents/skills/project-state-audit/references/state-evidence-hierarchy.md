# State Evidence Hierarchy — 使用細節

補充 SKILL.md 的六層證據排序，說明如何在實務中判斷「這個結論屬於哪一層」。

## 各層級的判斷方式

1. **實際 runtime / hosted 證據**：你或使用者剛剛實際執行/查詢過目標環境
   得到的結果。例如：實際呼叫某個 API 拿到的回應、實際查詢遠端資料庫拿到
   的筆數。
2. **可重現測試結果**：本輪或最近一輪實際執行過的測試/建置指令，且結果
   可以重跑得到一致的結論。
3. **Git tree 與 commit 歷史**：`git log`、`git show`、`git diff` 等指令
   讀到的實際歷史紀錄，代表「確實發生過的變更」，但不代表「變更後的行為
   一定符合預期」（那需要第 1、2 層驗證）。
4. **目前程式碼與設定**：直接讀取的原始碼、設定檔內容，是「現在寫的是
   什麼」，但不代表「執行起來會怎樣」。
5. **狀態文件**：長期維護的狀態追蹤、決策紀錄、handoff、README 等文件，
   代表「某個時間點有人記錄的說法」，可靠度取決於最後更新時間與維護頻率。
6. **對話記憶與摘要**：先前對話中的印象、AI 自己生成的摘要，最容易失真，
   僅供參考方向，不得單獨作為結論依據。

## 衝突處理原則

- 高層級證據與低層級證據衝突時，以高層級為準，並在報告中明確指出「文件說
  A，但實測結果是 B」，而不是選擇性只呈現其中一個。
- 若同一層級內部出現衝突（例如兩份狀態文件互相矛盾），視為「需要 owner
  確認」的情況，不得自行判斷哪一份對，保留兩者並列出矛盾點。
- 若完全沒有第 1-4 層證據、只能依賴第 5、6 層，結論必須明確標註證據層級
  為 5 或 6，並在最終報告的「未驗證」分類中列出，不得包裝成「已確認」。

## 常見誤用

- 把「程式碼看起來應該這樣運作」（第 4 層的推論）當成「已經驗證這樣運作」
  （第 1、2 層），這是最常見的層級混淆。
- 把「狀態文件說已完成」直接當作「已完成」，卻沒有交叉核對第 1-4 層證據。
- 把上一輪對話的摘要當成本輪的現況，卻沒有重新確認 Git 狀態是否已經改變。
