# Example: Status Document Sweep (illustrative only)

情境：一份長期維護的狀態追蹤文件裡有以下幾句話，需要在更新前先分類。

```text
原文 1: "匯出功能尚未支援 CSV 格式。"
現況查證: 程式碼確認匯出模組目前只支援 JSON。
分類: 正確的否定句 → 原樣保留。

原文 2: "2026-05 決定改用方案 B 處理排程。"
現況查證: git log 顯示 2026-07 又改回方案 A，並記錄了新的決策說明。
分類: 被 superseded → 保留原句並標記 (superseded by 2026-07 決定，見下方)，
      新增一句記錄 2026-07 的決定，兩者並存。

原文 3: "上線後由 X 負責監控前兩週的錯誤率。"
現況查證: 本輪無法確認 X 是否仍是負責人。
分類: 尚未確認 → 保留原句，加註「[待確認：X 是否仍為現任負責人]」。

原文 4: "已知问题：排序在奇數長度陣列上會出錯（見 issue #1234）。"
現況查證: 對應修復已合併且通過 regression-negative-proof 驗證。
分類: 真正過時 → 更新為「已修復（見 issue #1234，修復已通過負向/正向證明）」，
      原始問題描述改列為 [Historical] 保留在變更紀錄區。

原文 5: "目前排程系統無法支援跨時區任務（設計已知限制）。"
現況查證: 程式碼與文件皆未變更，此限制仍然成立。
分類: 仍為 active blocker → 原樣保留，不因文件偏舊而移除。
```

## 這個範例刻意示範的重點

- 五句話五種分類，說明同一份文件裡不可能用單一規則批次處理。
- 每筆分類都寫出了「現況查證」依據，而不是憑直覺判斷。
- 「被 superseded」與「真正過時」的處理方式不同：前者新舊並存，後者更新
  正文但把舊描述移到歷史區保留，兩者都不是直接刪除消失。
