# SOP-知識編譯工作流

> 目標：不要只把資料存進來，而是把每一次閱讀都編譯成會累積、會交叉引用、會越用越聰明的持久 Wiki。

## 一句話原則

不是問「這份資料要不要存」。

而是問「這份資料進來後，Wiki 哪裡應該永久改變」。

## 三層結構

### 1. 原始資料層 Raw Sources

放原文、逐字稿、PDF、網頁剪藏、暫存資料。

建議位置：

- `Inbox/`
- `obsidian-vault/00-收件匣/`
- `obsidian-vault/02-文獻與期刊/`

原則：

- 保留原貌
- 不把詮釋直接寫回原始來源
- 它是證據，不是最後的知識頁

### 2. 編譯後 Wiki 層 Compiled Wiki

放知識卡、概念卡、人物框架卡、判讀卡、MOC、SOP。

建議位置：

- `obsidian-vault/04-知識卡片/`
- `obsidian-vault/01-專家與MOC/`
- `obsidian-vault/03-診斷與檢查/`
- `obsidian-vault/05-營運SOP與模板/`

原則：

- 優先更新舊頁，不要一直開新頁
- 讓新資料去改變既有知識
- 顯式標記矛盾、邊界、例外

### 3. 規則層 Schema / Protocol

放結構規則、模板、工作流。

關鍵文件：

- `KNOWLEDGE-COMPILER-PROTOCOL.md`
- `SYSTEM-MEMORY-SCHEMA.md`
- `.agents/workflows/knowledge-compiler.md`
- `obsidian-vault/06-模板 (Templates)/知識編譯頁-WikiNote.md`

## 五個核心動作

### 1. 攝入 Ingest

當你看到好文章、好逐字稿、好論文：

1. 先收進原始資料層
2. 記一句「為什麼值得收」
3. 不急著立刻變成最終卡片

最低要求：

- 題目
- 來源類型
- 日期
- 收這份資料的理由

### 2. 編譯 Compile

讀完後不要只做摘要，要回答：

1. 這份資料讓哪一個舊頁面應該改寫？
2. 有沒有新的概念、機制、框架值得獨立成卡？
3. 有沒有打臉舊理解、補強舊理解、或讓邊界更清楚？

編譯時優先順序：

1. 先更新現有卡片
2. 再更新 MOC
3. 最後才新增卡片

### 3. 查詢 Query

問問題時，先查編譯後 Wiki，不要先回到原始 PDF。

只有在以下情況才回原始來源：

- Wiki 太薄
- 內容互相矛盾
- 需要精確數字或原文措辭

### 4. 回存 File Back

如果一次查詢產生了很好的產物，不要讓它消失。

適合回存的內容：

- 對比表格
- 深度分析
- 觀點衝突整理
- 決策框架
- 適合未來重複使用的回答

回存位置可以是：

- 現有卡片新增一節
- 新知識卡
- MOC 補一段導航
- SOP 升級

### 5. 體檢 Lint

固定做 Wiki 健康檢查，至少看五件事：

1. 有沒有重複卡片
2. 有沒有孤島頁面
3. 有沒有舊摘要沒有更新
4. 有沒有矛盾沒標出來
5. 有沒有原始資料一直進來但從沒被編譯

## 每次閱讀後必問四題

1. 這次新進來的東西，哪一點會在未來反覆有用？
2. 它應該改哪一張舊卡？
3. 它揭露了什麼矛盾、邊界或例外？
4. 它應該落成：
   - 文獻卡
   - 概念卡
   - 人物／框架卡
   - 判讀卡
   - MOC 更新
   - SOP 更新

如果四題都答不出來，代表你只是「收了資料」，還沒真的完成知識編譯。

## 推薦日常節奏

### 快速版：10 到 15 分鐘

適合日常看到一篇好文章時：

1. 收資料
2. 寫一句為什麼重要
3. 更新一張舊卡或新建一張最小卡片
4. 補兩個連結

### 深度版：30 到 60 分鐘

適合論文、逐字稿、重要訪談：

1. 保存原始來源
2. 抽出 3 到 5 個核心命題
3. 決定影響到哪些舊卡
4. 更新卡片與 MOC
5. 把本次最有價值的分析另存回 Wiki
6. 標記尚未解的矛盾與下一步

## 什麼時候不用新增卡片

不要為了勤勞而製造雜訊。以下情況優先更新舊頁：

- 只是補證據，不是新概念
- 只是細化既有機制
- 只是替某個老問題補一個例子
- 只是讓某個主題頁更完整

## 成功標準

這套工作流有跑起來，會出現這些現象：

- 你問同樣類型的問題，越來越不用回頭翻原始資料
- 舊卡片會被新資料持續改寫
- MOC 會越來越像導航系統，不只是目錄
- AI 的好回答不再消失，而是變成新資產
- 你的知識庫越用越像活體 Wiki，而不是 PDF 倉庫
